# data/reviews/ — split review (human decisions)

Tracked in git. Decisions here change which split each recall belongs to, so they must be
made by **named team members**, never by an AI tool.

| File | Who edits it | Purpose |
| --- | --- | --- |
| `split_pair_review.csv` | **Human reviewers** | One row per recall pair to decide |
| `split_pair_review.meta.json` | generated | Export time, corpus + split fingerprints, counts |
| `assistant_proposals.json` | generated by the AI assistant | Suggestions only — shown in `assistant_*` columns, **never** counted as a decision |

`url_a/b`, `jaccard`, `cosine`, `assistant_proposal`, `assistant_flag`,

`reviewed_at`, `corpus_fingerprint`.

## Decisions

| Decision | Meaning | Effect on splits |
| --- | --- | --- |
| `SAME_PRODUCT` | Same product: re-notice, expansion, re-announcement, size/flavour variant of one recall | **Always** kept in one split |
| `RELATED_EVENT` | Different products tied to one recall event, company action, supplier or outbreak | Policy below |
| `DISTINCT` | Only the product type is similar | No constraint; pair leaves the residual-risk list. A manual link marked `DISTINCT` is removed |

### RELATED_EVENT policy (documented decision)
**Default: `colocate`** — RELATED_EVENT pairs are kept in one split, like SAME_PRODUCT.
Reason: notices from one event share hazard wording, dates and often supplier names; if one
is used for training Model B and the other is a test target, the model can match on
event-specific wording rather than on the consumer's need, inflating test scores. Keeping
them together costs a little split balance and nothing else.
The alternative `--related-event-policy allow-cross-split` lets them stay apart; the
manifest then records each such pair as an *accepted risk*, and results must be reported
with that caveat. Changing the policy after annotation starts requires re-validation.

Embedding similarity alone **never** merges records: the semantic audit only nominates
pairs for this review.

## How to review (per row)
1. Open **both** `url_a` and `url_b` (official recall pages). Compare product, brand,
   company, dates, lot codes and hazard. The assistant did **not** open these pages.
2. Choose `decision`. Use `assistant_proposal` only as a hint — rows flagged
   `check_source` or `questionable_link` need particular care.
3. Fill `reviewer` (your full name or initials — AI/assistant names are rejected),
   `rationale` (your own words, ≥ 10 characters; copying the assistant text is rejected),
   `reviewed_at` (YYYY-MM-DD) and `corpus_fingerprint` (printed by `status`).
4. Keep the CSV as UTF-8 CSV when saving from a spreadsheet; do not change ids or columns.

Ideally two people review independently and resolve disagreements before applying.

## Commands
```bash
python -m evaluation.split_review status    # progress + validation errors + fingerprint to enter
python -m evaluation.split_review apply     # only works when every row has a valid human decision
python -m evaluation.split_review export    # refresh after apply if new pairs appear (keeps decisions)
```
`apply` rebuilds the split, verifies every SAME_PRODUCT (and colocated RELATED_EVENT) pair
shares a split, and **freezes** the manifest — unless the rebuild exposes new unreviewed
cross-split pairs, in which case it exits 4: export, review the new rows, apply again.
A frozen manifest cannot be overwritten by `evaluation.splits` (even with `--force`);
deliberate changes need `apply --refreeze`. Freeze **before** writing evaluation queries.

### Review all candidates at once (`export --all-candidates`)
`apply` reshuffles the split when review decisions change the groups, so a plain `export`
can expose a new batch of crossing pairs after every round. `export --all-candidates` lists
**every** lexical candidate (Jaccard 0.4–0.6) and every MiniLM pair with cosine ≥ 0.85,
whatever its current split, except pairs already inside one merged group (those always share
a split). Once all of them are decided, a rebuild cannot expose an unreviewed candidate.
It needs the current MiniLM embeddings and refuses to run without them. Existing human
columns are never overwritten. Keep using `--all-candidates`: a later plain `export` drops
undecided rows that do not currently cross splits.
